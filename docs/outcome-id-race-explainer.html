How a temporary outcome ID can reach the PATCH endpoint

New outcomes start with a client-side UUID so the editor can track them before they exist in the database. The API requires a MongoDB ID for updates. The error happens when the builder tries to PATCH before it has a valid database ID to use.

The two-ID lifecycle

The builder keeps a stable local key for the editor and receives a separate persisted ID from the create request.

1

Outcome is added locally

4

The update path should substitute serviceId for the temporary local id.

Where the race appears

The store’s update method only replaces the local ID when serviceId is present. If the update path runs with no persisted ID, the outcome service uses outcome.id as-is.

Expected path

The create response has arrived and the outcome has a persisted ID.

PATCH /learning-outcomes/66f15a9e08b93b4c2d…

Observed failing path

The request URL contains the local UUID. The backend validates it as outcomeId and rejects it.

PATCH /learning-outcomes/72f3bb67-f3db-49b1-8ab7-1e33f723adff
What the URL proves: the PATCH service received the UUID as its ID argument. It does not prove by itself why serviceId was missing. The key facts to inspect are the PATCH body and the preceding POST response: whether POST succeeded, and whether its response contains the ID in the shape the client reads (response.id).

A safe fix

Keep edits queued while creation is pending, then flush them using the ID returned by the API. That avoids sending an update against an outcome that does not yet have a database identity.

  1. Track creation state per outcome. Distinguish local, creating, created, and failed outcomes rather than relying only on membership in newOutcomes.
  2. Serialize create and update. Do not let the update path call PATCH until the create promise has succeeded and a MongoDB ID is stored.
  3. Normalize the create response. Confirm the API response shape and read its actual ID field before marking the outcome as persisted.
  4. Guard the API service. Reject a UUID before constructing a PATCH request, so an invalid request is caught at the client boundary with a useful error.
